# Модуль 6.1. Домашнє завдання: Багатозадачність у FreeRTOS

Цей проєкт демонструє перехід від підходу **Superloop** (один нескінченний цикл із ручною перевіркою таймерів) до повноцінної архітектури реального часу **FreeRTOS** на базі фреймворку **ESP-IDF**.

Програма керує трьома світлодіодами з різними інтервалами блимання, де кожен світлодіод працює у власній незалежній задачі (потоці) під керуванням планувальника ОС.

> 🔗 **Попередня версія (до FreeRTOS):** реалізацію через неблокуючі таймери (`esp_timer_get_time`) можна переглянути за посиланням [module_2.3 (Superloop & Timers)](https://github.com/bohdan-satyr/beetroot-embedded-course/tree/main/homeworks/module_2.3).

## 🚀 Особливості реалізації

1. **Параметризована задача (`led_blink_task`)**: Замість дублювання коду створено одну універсальну функцію задачі. Через вказівник `void *pvParameters` у кожен екземпляр передається структура `led_config_t` з номером піна та індивідуальним інтервалом.
2. **Створення задач через `xTaskCreate`**: У функції `app_main()` ініціалізуються три окремі задачі з виділеним стеком (`2048` байт) та однаковим пріоритетом. Після запуску задач сама `app_main` завершує роботу, звільняючи ресурси.
3. **Апаратно-незалежні затримки**: Використовується функція `vTaskDelay(pdMS_TO_TICKS(ms))`, яка автоматично переводить мілісекунди у системні тіки FreeRTOS незалежно від налаштувань частоти ядра в `menuconfig`.
4. **Зчитування стану піна**: Піни налаштовані в режим **`GPIO_MODE_INPUT_OUTPUT`**, що дозволяє інвертувати їхній поточний стан однією командою `!gpio_get_level()`.

## ⚖️ Порівняння підходів: Superloop vs FreeRTOS

Перехід від попередньої версії коду до використання функціоналу FreeRTOS дав такі переваги:

| Критерій | Старий підхід (Superloop + `esp_timer`) | Новий підхід (FreeRTOS + `xTaskCreate`) |
| :--- | :--- | :--- |
| **Архітектура** | Усі процеси змішані в одному циклі `while(1)` всередині `app_main`. | Кожен процес ізольований у власній незалежній задачі (Task). |
| **Використання CPU** | Постійне опитування таймера (`polling`) кожну мілісекунду навіть без потреби. | Під час `vTaskDelay()` задача переходить у стан *Blocked* і не витрачає ресурси процесора. |
| **Масштабованість** | Додавання нової логіки ускладнює цикл і може збити таймінги інших процесів. | Нові функції додаються як окремі задачі з власними пріоритетами. |
| **Читабельність коду** | Потрібно вручну зберігати та порівнювати мітки часу (`storedTimeStamp`) для кожного піна. | Логіка виглядає лінійно та просто, як звичайний `delay`, але без блокування системи. |
| **Робота з ядрами** | Увесь код виконується послідовно в одному потоці. | Планувальник може автоматично розподіляти задачі між обома ядрами **ESP32-S3** (або закріпити їх через `xTaskCreatePinnedToCore`). |

## 📂 Структура проєкту

Проєкт має стандартну структуру для зв'язки PlatformIO + ESP-IDF фреймворку:

```text
├── results/              # Відео результату роботи
├── CMakeLists.txt        # Кореневий файл конфігурації CMake (ініціалізує ESP-IDF)
├── platformio.ini        # Конфігурація платформи PlatformIO (плата, фреймворк, швидкість порту)
├── src/
│   ├── CMakeLists.txt    # Файл реєстрації компонентів для CMake
│   └── main.c            # Основний вихідний код програми на мові C
└── README.md             # Документація проєкту
```

## 🛠️ Вимоги та налаштування

Для збірки та прошивки проєкту вам знадобляться:
* **VS Code** із встановленим розширенням **PlatformIO IDE**.
* Плата розробника на базі чипа **ESP32-S3** (за замовчуванням конфіг налаштований під `esp32-s3-devkitc-1`).

### Налаштування `platformio.ini`
Переконайтеся, що ваш файл конфігурації виглядає наступним чином:

```ini
[env:esp32-s3-devkitc-1]
platform = espressif32
board = esp32-s3-devkitc-1
framework = espidf
monitor_speed = 115200
```
